# 知识条目编写规范（AUTHORING_SPEC v1）

> 2026-11-17 立。这份文件管"一条知识怎么写"，`docs/KNOWLEDGE_FORMAT.md` 管"字段长什么样"。
> 改这份规范之前先改这里，再改代码——顺序反了，代码和规矩就会各说各话。

## 核心工作

把开发者的自然语言需求，转化成结构化、可检索、可复用的编程知识条目。

不是代码生成器。先理解用户可能怎么描述这件事，再映射到统一的知识模型。
数据准确性、完整性、可检索性，优先于文字数量。

## 1. 双基元：Object + Action

每条知识条目有且只有一个主要 Object 和一个主要 Action。

- **Object**：用户想操作、查询或改变的对象（文件后缀、列表、字典、进程…）
- **Action**：用户想对 Object 做什么（判断、获取、删除、遍历…）

两者都必须带 `id` / `name` / `aliases`，且 `id` **必须在受控词表里**：

```
src/starport_dictionary/knowledge/primitives.py   ← 唯一事实源
docs/SEMANTIC_PRIMITIVES.md                       ← 由上面的文件生成，供人查阅
```

### 词表维护三条规矩

1. 加新条目前先查已有 Object / Action，语义一致就必须复用。
2. 不因为中文名称不同就新建 ID（"文件后缀"和"扩展名"是同一个 `file.extension`）。
3. 只有真正不同的技术对象或动作才新建 ID，且必须写清含义和适用范围。

**不这么做，二十条之后就会出现 `file.ext` / `file.suffix` / `file.extension` 三种写法，跨条目聚合直接失效。** 这是这个项目最容易崩的地方。

## 2. 必须支持五种检索入口

1. 只搜 Object
2. 只搜 Action
3. Object + Action
4. 自然语言表达
5. 技术术语

## 3. 六类用户说法（utterances）

| 类别 | 举例 |
|---|---|
| `direct` | 判断文件后缀 |
| `questions` | 怎么判断文件后缀？ |
| `colloquial` | 看看是不是 py 文件 |
| `goal_based` | 只处理 Python 文件 |
| `technical` | pathlib suffix / Path.suffix |
| `short_queries` | 后缀 / 扩展名 / suffix / .py |

**硬性要求**：`direct`、`questions`、`colloquial`、`short_queries` 四类必须有；总数至少 8 条。
不要为了凑数写重复句子——同一句话换个标点不算一条。

## 4. ⚠ utterance 不进索引

这是本项目最重要的一条设计约束：

```
索引里只放：title + object 名称/别名 + action 名称/别名 + targets
utterance 只当测试集
```

**为什么**：如果把用户原话也存进索引，那"用原话搜原话"必然命中，测试恒真，及格率 100%，但真实用户说一句没被收录的话照样搜不到。

判据：**一条 utterance 如果只能靠它自己命中，它就是在自证，不算数。**

## 5. 歧义不得强行合并

「判断文件后缀」和「识别文件真实格式」不是同一个需求：后者要读文件头。

对歧义表达：
1. 标记可能的不同意图；
2. 关联多个候选条目；
3. 必要时标记 `ambiguity`；
4. 不得擅自确定唯一答案。

```yaml
ambiguity:
  - note: 用户要的可能是"真实格式"，光看后缀不够
    candidate_ids: [py.fs.real_type]
```

## 6. 代码要求

1. 语法正确；2. 每个关键语句都能解释；3. 写明语言与版本；
4. 实现清晰易懂；5. 说明边界条件；6. 不虚构不存在的 API；7. 不把特殊场景写成通用方案。

**没实际跑过，不得标 `tested`。**

## 7. 语句解释 vs 原理解释

- 语句解释回答：这段代码里的语法是什么、干什么用、返回什么、容易混在哪儿。
- 原理解释回答：它为什么能实现这个功能。

不合格：`"Path()"：Path 函数。`
合格：`"Path()"：创建一个路径对象，让后面的操作都走 pathlib 的接口，而不是手工拼字符串。`

没依据不要编造底层实现细节。

## 8. satisfied 相关的字段规则

- `tested_versions` 写**实际跑过的具体版本**（枚举），不写 `3.10+`。
- 写了 `tested_versions` 就必须写 `min_version`，程序用它算版本范围。
- 缺测的版本显示"未测"，不是"不支持"——这两件事不能混。

## 9. related_ids

必须指向真实存在或明确规划的条目。建议关联：同 Object 的其他 Action、同 Action 的其他 Object、前置知识、替代方案。
不得为了凑数建联系。

## 10. 输出与审核

写或改一条条目时，要能回答：

1. 完整 Markdown 条目
2. 用了哪个 Object ID
3. 用了哪个 Action ID
4. 新增了哪些自然语言表达
5. 有哪些地方可能歧义
6. 关联了哪些条目
7. 哪些内容还没验证

**不得擅自修改已发布的标准 Object / Action ID。** 要改知识模型，先提修改建议。

## 11. 最终原则

这个项目不是收集尽可能多的代码，而是建立一套"自然语言需求 → 结构化技术知识"的映射体系。

同一份知识，必须能通过不同的自然语言入口被检索到。
